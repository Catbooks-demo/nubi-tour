# 누비투어 — 패키지여행 예약 사이트 설계

2026-11-17, 예진 님과 정함. 이름 "누비투어"는 임시(실제 회사와 겹치지 않는 이름이면 바꿔도 됨).

## 왜
AXcellent를 제대로 시험하려면 AXcellent 규격에 맞춰 만든 사이트(캣북스)만으로는 부족하다. AXcellent를 전혀 모르고 만든, **진짜로 돌아가는 여행사 사이트**가 하나 있어야 사이트 연결 설계의 "직접 만든 사이트(쇼핑몰 아님) — 이미 있는 API·인증 또는 읽기 전용 DB 계정으로 연결, '예약 = 주문' 같은 항목 짝 맞추기" 경로를 실제로 시험할 수 있다.

그래서 이 사이트는 **AXcellent와 독립적**이다. AXcellent용 주소·이벤트·규격을 넣지 않는다. 실제 여행사가 자기 필요로 만들었을 기능(직원용 관리 화면, 외부 시스템용 API 키, 상태 확인 주소, 로그)만 있다. AXcellent는 나중에 다른 고객사처럼 바깥에서 붙는다.

## 목표
- 손님이 패키지 상품을 찾고 → 출발일·인원을 골라 → 예약하고 → 예약금을 결제하고 → 잔금을 내고 → 취소·문의·후기까지 할 수 있는, 처음부터 끝까지 실제로 동작하는 사이트.
- 여행사 직원이 상품·출발일·예약·취소·문의를 처리하는 관리 화면.
- 실제 여행사 규칙: 국외여행 표준약관의 취소 수수료, 최소 출발 인원과 출발 확정, 예약금 기한, 잔여석.
- 운영하는 서비스처럼: 회원 비밀번호는 해시, 세션 만료, 시도 제한, 상태 확인 주소, 구조화된 로그, DB 마이그레이션, 백업 가능한 PostgreSQL.

## 하지 않을 것 (이번)
- 항공권·호텔 단품 판매, 실제 항공·호텔 예약 시스템(GDS) 연동. 패키지 가격에 포함된 것으로 다룬다.
- AXcellent 연결 작업, AXcellent용 코드·규격·이벤트. 가상 고객·가상 예약 데이터 생성기(사이트가 생긴 뒤 다음 단계).
- 실제 돈이 오가는 결제(토스 **테스트 키만** 받는다. `live_` 키면 시작을 거부).
- 문자·카카오 알림톡·이메일 실제 발송(발송 기록만 DB에 남기는 "보낸 편지함" 화면으로 대신).

## 하면 안 되는 것
- 실제 여행사(하나투어·모두투어·노랑풍선·인터파크 등)의 이름·로고·문구·화면을 베끼거나 그 회사인 것처럼 보이게 하기. 구성(목록·달력·일정표·포함/불포함)만 참고한다.
- 사업자등록번호·관광사업 등록번호·영업보증보험 같은 실제처럼 보이는 법적 번호를 지어내 넣기. 푸터에는 "시연용 가상 여행사" 표시와 빈칸 형식만.
- 키·비밀번호를 레포·로그·화면에 남기기. 공개 레포에 실제 내부 주소 넣기.

## 정한 것

### 기술 (예진 님이 "독립 사이트로" 맡김 → 제가 정함)
- **Next.js (App Router, TypeScript)** 하나로 손님 화면·관리 화면·API(Route Handlers)를 함께 만든다. 실제 중소 여행사 사이트에 흔한 구조이고 배포 단위가 하나다.
- **PostgreSQL** + **Prisma**(스키마·마이그레이션). 읽기 전용 DB 계정 연결 시험이 가능하다.
- **Tailwind CSS**. 외부 UI 키트 없음.
- 결제: **토스페이먼츠 결제위젯 테스트 모드**. 키가 없으면 "모의 결제" 버튼으로 같은 흐름을 탄다.
- 실행: `docker compose`(app + postgres). 개발은 `npm run dev` + 로컬 postgres(compose의 db만).
- 시험: Vitest(규칙·API), Playwright(핵심 손님 흐름 1~2개). CI: GitHub Actions(타입 검사·린트·시험·빌드).

### 데이터 (핵심 표)
- `Region`(대륙·나라·도시), `Theme`(가족·허니문·효도·자유일정 등)
- `Product` 패키지 상품: 코드(예 `NB-JP-OSA-04`), 이름, 지역, 테마, 박·일, 항공사·출발 공항, 대표 이미지, 요약, 포함/불포함, 선택관광, 쇼핑 횟수, 가이드·인솔자, 여권·비자 안내, 판매 중 여부.
- `ItineraryDay` 일차별 일정(도시, 내용, 식사 조식/중식/석식, 숙소).
- `Departure` 출발일: 상품, 출발일·귀국일, 정원, 최소 출발 인원, 성인/아동/유아 가격, 싱글차지, 상태(`모객중`·`출발확정`·`마감`·`출발취소`·`출발완료`), 예약된 좌석(계산값).
- `User` 회원(이메일·비밀번호 해시·이름·전화·마케팅 동의), `Session`.
- `Booking` 예약: 예약번호(예 `NB2611170001`), 회원, 출발일, 대표 예약자 연락처, 인원(성인·아동·유아), 싱글룸 수, 총액, 예약금, 잔금, 잔금 기한, 상태, 만든 시각·바뀐 시각.
- `Traveler` 여행자(영문 이름, 성별, 생년월일, 여권번호 뒤 4자리만 화면 표시·저장은 암호화 또는 생략).
- `Payment` 결제(예약금/잔금/환불, 금액, 수단, 토스 결제키, 상태, 시각).
- `Cancellation` 취소(요청 시각, 사유, 기준일 수, 수수료율, 수수료, 환불액, 처리자, 상태).
- `Inquiry` 1:1 문의(분류, 예약 연결, 내용, 답변, 상태), `Review` 여행 후기(완료된 예약만, 별점·내용·사진 없음).
- `Notice` 공지·FAQ, `Message` 보낸 편지함(종류·받는 사람·내용·시각), `Staff` 직원 계정(역할 `admin`·`agent`), `ApiKey`(외부 시스템용, 이름·범위 `read`/`write`·해시·마지막 사용), `AuditLog` 관리 작업 기록.

### 규칙
- **가격**: 아동(만 12세 미만) = 상품별 아동가(기본 성인가의 90%), 유아(만 2세 미만) = 상품별 유아가(기본 성인가의 10%, 좌석 없음). 싱글차지는 방 수만큼. 유류할증료는 가격에 포함(별도 표시만).
- **좌석**: 성인+아동이 좌석을 쓴다. 예약 시 좌석을 잡고(동시 예약에도 정원을 넘지 않게 DB 트랜잭션·잠금), 취소·기한 만료 시 돌려놓는다. 남은 좌석이 0이면 `마감`.
- **예약금**: 1인 30만 원(상품별로 바꿀 수 있음) × 좌석 인원, 예약 후 **24시간 안에** 내야 한다. 못 내면 예약 자동 취소(작업은 주기 실행, 아래).
- **잔금**: 출발 **7일 전**까지. 못 내면 직원 확인 대상 목록에 올린다(자동 취소하지 않음 — 실제 여행사처럼 연락 후 처리).
- **출발 확정**: 예약금까지 낸 좌석 인원이 최소 출발 인원 이상이면 `출발확정`. 출발 7일 전까지 못 채우면 직원이 `출발취소` 할 수 있고, 그 출발일 예약은 **전액 환불**(여행사 사정 취소).
- **손님 취소 수수료 (국외여행 표준약관 기준, 여행 요금 대비)**: 출발 30일 전까지 0%(예약금 전액 환불) / 29~20일 전 10% / 19~10일 전 15% / 9~8일 전 20% / 7~1일 전 30% / 당일 50%. 일 수는 한국 시간 날짜 기준. 환불액 = 낸 금액 − 수수료(음수면 0, 덜 낸 수수료는 청구하지 않음 — 화면에 안내).
- **상태 흐름**: 예약 `결제대기` → `예약금완료` → `완납` → `여행완료` / 어느 단계에서든 `취소요청` → `취소완료`, `결제대기`에서 기한 만료 → `기한만료취소`. 손님 취소는 직원 승인 뒤 환불(토스 테스트 취소 API 또는 모의 환불).
- **주기 작업**: 앱 안의 예약 작업(매 5분): 예약금 기한 만료 처리, 출발 확정 계산, 출발일 지난 예약 `여행완료`, 잔금 기한 임박 안내 기록. 같은 작업이 두 번 돌아도 결과가 같게.
- **시간**: 저장은 UTC, 화면·날짜 계산은 한국 시간.

### 세부 규칙 (검토 뒤 제가 정함 — 예진 님 확인 대상)
- **수수료 기준 금액** = 그 예약의 여행 요금 총액(성인·아동·유아·싱글차지 모두 포함). 수수료 = 총액 × 비율(원 단위 내림). 환불액 = 지금까지 낸 금액 − 수수료, 0보다 작으면 0(모자란 수수료는 청구하지 않음). 30일 전까지는 수수료 0이라 낸 금액 전부 환불.
- **출발 임박 예약**: 출발 8일 이상 남았으면 예약금(24시간 기한) + 잔금(출발 7일 전 기한). **출발 7일 이내**면 예약금 없이 **총액 한 번에**, 기한은 24시간과 출발 전날 23:59 중 이른 쪽. **출발 2일 이내**는 온라인 예약 불가("전화 문의" 안내).
- **출발 확정 셈**: 상태가 `예약금완료`·`완납`인 예약의 좌석 인원(성인+아동) 합.
- **출발취소(여행사 사정)**: 그 출발일의 살아 있는 예약은 `취소요청`을 거치지 않고 바로 `취소완료`, 수수료 0, 낸 금액 전액 환불, 손님 알림 기록.
- **결제 기록**: `Payment`는 바꾸지 않고 쌓는다. 환불도 음수가 아닌 `kind=refund` 행(원결제 id를 가리킴). 부분 환불은 가장 최근 결제부터 거꾸로 나눠 돌려준다. 모의 결제도 같은 표·같은 흐름(수단 `mock`).
- **나이 기준**: 출발일 기준 만 나이. 아동·유아 가격은 출발일마다 값이 있다(기본값 90%·10%로 채움). 성인 1명 이상 필수, 유아 수 ≤ 성인 수, 한 예약 최대 9명.
- **비회원 예약 허용**: `Booking.user_id`는 비어 있을 수 있다. 비회원은 예약할 때 조회 비밀번호(4~6자리 숫자, 해시 저장)를 정하고, 예약번호 + 휴대폰 + 조회 비밀번호로 조회·잔금 결제·취소 신청.
- **외부 API 개인정보**: 범위 `read`는 여행자 이름·연락처를 가려서(예 `김*진`, `010-****-1234`) 내보내고, 별도 범위 `read_pii`가 있어야 원문을 준다. 여권번호는 어떤 범위로도 안 나간다. 목록은 `updated_since` + 커서(`updated_at`,`id`) 페이지. 삭제 대신 상태로 남기므로 삭제 표시는 없다.
- **DB 이름**: 표·컬럼은 영어 snake_case(`bookings`, `departure_id` …). 상태 값도 영어 코드(`pending_deposit`, `deposit_paid`, `fully_paid`, `completed`, `cancel_requested`, `cancelled`, `expired`)로 저장하고 화면에서 한국어로 보여 준다. 읽기 전용 DB 계정이 보는 계약이 되므로 마이그레이션으로만 바꾼다.
- **실행 구성**: 앱 컨테이너 하나를 기본으로 하되, 주기 작업은 PostgreSQL advisory lock으로 한 번에 하나만 돈다(여러 개 띄워도 안전).

### 화면 (손님)
- 메인: 검색창(어디로·언제·몇 명), 지역 바로가기, 테마 기획전, 출발 확정 임박 상품, 특가, 공지.
- 상품 목록: 지역·출발월·박수·가격대·항공사·출발확정만 필터, 정렬(추천·가격·출발일).
- 상품 상세: 사진, 요약 아이콘(박·일, 항공, 쇼핑 횟수, 가이드), **출발일 달력**(날짜별 가격·상태·남은 좌석), 일정표(일차별 접기), 포함/불포함, 선택관광, 취소 규정, 후기.
- 예약: 인원·싱글룸 → 대표 예약자 → 여행자 정보 → 약관 동의(여행약관·개인정보·취소 규정) → 예약금 결제 → 완료(예약번호).
- 마이페이지: 예약 목록·상세(상태, 결제 내역, 잔금 결제, 취소 신청과 예상 환불액 미리 보기), 문의, 후기 쓰기, 회원 정보.
- 고객센터: 공지·FAQ·1:1 문의, 여행약관·개인정보 처리방침·취소 규정 페이지.
- 비회원 예약 조회(예약번호 + 대표 예약자 휴대폰).

### 화면 (직원, `/admin`, 직원 계정 로그인)
- 대시보드: 오늘 예약·결제·취소 요청·미답변 문의·잔금 미납·출발 확정 대기.
- 상품·일정·출발일 관리(만들기·수정·판매 중지, 출발일 상태 바꾸기).
- 예약 목록·상세(검색, 상태 바꾸기, 메모), 취소 요청 승인/거절(수수료 자동 계산, 직원이 조정 시 사유 필수).
- 문의 답변, 후기 숨기기, 공지 관리, 보낸 편지함, 직원·API 키 관리(관리자만), 작업 기록.

### 외부 시스템용 API (실제 여행사가 ERP·정산 시스템용으로 열어 둘 법한 것)
- `/api/v1/...` 에 `Authorization: Bearer <API 키>`. 범위 `read`: 상품·출발일·예약·결제·취소·문의 목록/상세(변경 시각 이후로 거르기, 페이지 나누기). 범위 `write`: 문의 답변, 예약 메모, 출발일 상태 바꾸기 정도.
- 이 API의 모양은 **여행사 자기 기준**이다(필드 이름·상태 값 모두 여행사 용어). AXcellent 규격에 맞추지 않는다.
- OpenAPI 문서(`/api/v1/openapi.json`)를 함께 낸다.

### 운영
- `/healthz`(앱), `/readyz`(DB 연결), JSON 한 줄 로그(요청 id·경로·상태·시간, 개인정보·키 제외).
- 비밀번호 scrypt 또는 argon2 해시, 세션 쿠키(HttpOnly·SameSite), 로그인·가입 시도 제한, 관리 화면은 직원 계정만.
- 개인정보: 여권번호는 저장하지 않거나 암호화(만드는 사람이 고름), 화면에는 뒤 4자리만.
- `.env.example`만 레포에. 시드: 지역·테마·상품 약 40개(일본·동남아·중국·유럽·미주·대양주), 출발일은 실행 날짜 기준 앞으로 3개월, 직원 계정 1개(비밀번호는 시드 실행 시 환경변수로).
- 이미지: 외부 사진을 내려받아 레포에 넣지 않는다. 지역별 일러스트/그라데이션 대표 이미지(SVG)로 시작하고, 나중에 팀이 라이선스가 확인된 사진을 주면 바꾼다.

## 방법 비교 (예진 님이 A를 고름)
- **A. 자기 규격의 독립 사이트 (고름)**: AXcellent가 낯선 사이트에 붙는 경로를 실제로 시험할 수 있다. 만드는 양이 가장 많다.
- B. 캣북스를 복사해 여행 상품으로 바꾸기: 빠르지만 AXcellent 입장에서 캣북스와 같은 연결이라 새로 시험할 게 없다.
- C. 화면만(가짜 데이터): 싸지만 AXcellent가 읽을 데이터가 없다.

## 만드는 사람에게 맡김
폴더 구조, 컴포넌트 나누기, 상품 40개 내용(가상의 일정이지만 실제 지명·자연스러운 동선), 화면 디자인(여행사다운 밝고 신뢰감 있는 톤, 고유 브랜드 색), 여권번호 저장 방식, 주기 작업 실행 방식(앱 안 스케줄러 또는 별도 프로세스), Playwright 흐름 선택.
